## Context

The brand handoff (`design_handoff_rhizome_brand_shell/`) specifies 15 named
color themes (Rhizome, Dracula, Nord, Gruvbox Dark/Light, Solarized
Light/Dark, Catppuccin Mocha/Latte, Tokyo Night, One Dark, Rosé Pine, GitHub
Light, Everforest, Monokai Pro) plus a user-selectable accent on the default
Rhizome theme. The app's existing theming is a single light/dark axis:
`data-theme="light"|"dark"` + a `.dark` class, applied by
`applyThemeModeToDocument` (`src/lib/themeMode.ts`) and driven by a
`theme_mode` setting resolved through Light/Dark/System.

13 of the 15 design themes are fixed-polarity (Dracula is always dark,
GitHub Light always light) — they aren't "a dark mode and a light mode,"
they're single skins. Only Rhizome has two poles and should keep following
the mode toggle.

## Decision

1. **New independent axis, not a replacement.** `data-color-theme="<slug>"`
   on `<html>`, orthogonal to the existing `data-theme`/`.dark` axis. Absence
   of the attribute (or `data-color-theme="rhizome"`) means the default
   theme — behaves exactly as today, mode-toggle-driven.
2. **Fixed themes pin polarity.** Selecting a fixed theme (e.g. `dracula`)
   forces `data-theme`/`.dark` to that theme's declared polarity, overriding
   whatever the Light/Dark/System toggle says. Every existing
   dark-conditional in the codebase (`.dark` selectors, `useDocumentThemeMode`
   consumers) keeps working unmodified — a fixed theme just always resolves
   to one side of that same existing switch.
3. **Accent remap stays on the `--accent-blue` family.** The whole codebase
   already keys UI action color off `--accent-blue`/`--primary`/`--ring`/
   `--link-color` (`sidebar-primary`, `border-focus`, etc. all alias it).
   Rather than introduce a parallel `--accent-primary` token and rewrite
   every consumer, `data-accent="<key>"` blocks remap the existing
   `--accent-blue*` family to one of the 8 hues `AccentColorPicker` already
   exposes (`ACCENT_COLOR_PICKER_KEYS`: red/orange/yellow/green/blue/purple/
   pink/gray — reused verbatim, not reinvented). Accent only applies on the
   default Rhizome theme; fixed themes own their own accent per the design
   docs and ignore `data-accent`.
4. **Generated CSS, not hand-written.** The 14 fixed-theme token blocks
   (`src/themes.css`) are generated by `scripts/generate-themes-css.mjs`
   from the 12-channel palette table in the brand handoff, deriving the
   remaining semantic tokens (hover/selected/popover/etc.) with the same
   mix ratios the hand-tuned `index.css` light/dark blocks use. Re-run the
   script rather than hand-editing `themes.css` if the source palette
   changes.
5. **Pre-hydration script duplicates the polarity map.** `index.html`'s
   inline bootstrap script (which already avoids a light/dark flash before
   React mounts) gets its own hardcoded copy of the slug→polarity map,
   since it can't import TypeScript. Comment-linked to `COLOR_THEMES` in
   `themeMode.ts` — keep both in sync by hand when adding a theme.
6. **Settings plumbing follows the existing per-setting template**
   (`agent_memory_vault_path`, ADR-0153): `color_theme`/`accent_color`
   fields in `settings.rs` with `normalize_*` + `SUPPORTED_*` consts, mirrored
   in `types.ts`/`useSettings.ts`/`mock-handlers.ts`, applied via
   `useThemeMode` (extended with two new optional params — existing 2-arg
   call sites are unaffected), surfaced in `AppearanceSettingsSection`.

## Consequences

- Adding a 16th theme means: one entry in the brand handoff's theme table,
  one entry in `themeMode.ts`'s `COLOR_THEMES`, one entry in the
  `index.html` polarity map, one entry in `settings.rs`'s
  `SUPPORTED_COLOR_THEMES`, and a re-run of `generate-themes-css.mjs`. Five
  touch points, all mechanical.
- Type directions (the brand handoff's 3 font-pairing options) are
  explicitly deferred — no token axis added for them yet. If revisited, the
  same `data-*` attribute pattern applies.
- The generated `themes.css` derivations (hover/selected/popover mixes) are
  judgment calls, not pixel-verified against the design docs beyond the 12
  source channels — acceptable per the plan's stated fidelity bar for
  non-core tokens.
