## 1. What "see the app directly" means here

The agent reads the **running page as data**: no pixels, no macOS permission.

| Signal | Source | In slice 1 |
|---|---|---|
| Layout findings (dead, duplicate, tiny, overlapping controls) | `auditUi()` in `src/utils/uiAudit.ts` | yes |
| Scroll wells: does a named panel scroll? (`overflow-y`, `scrollHeight`, `clientHeight`) | new `snapshotUi()` | yes. This is the class of bug that hid the transcript scroll box for 3 days. |
| Controls: role, accessible name or `data-testid`, box size | new `snapshotUi()` | yes |
| Console errors since load | Playwright `page.on('console')` | yes |
| App state (active note, open screen) | `window.__rhizomeTest` | read `activeTabPath` only |
| Native window (Rust menus, tray, folder prompts) | Tauri WKWebView | no. That needs a native path (§5, Q1). |

The page is the browser build (`pnpm dev`) at `BASE_URL`, default `http://localhost:5202`.

## 2. Smallest first PR

**`pnpm live-ui [--screen <name>]`**: a Node script that opens the running dev app in headless Playwright, walks the three screens `ui-audit.spec.ts` already walks, and prints one markdown block per screen to stdout. Example line:

```text
well  transcript  800x640  overflow-y: visible  scrollHeight=640  clientHeight=640  canScroll=false
```

- It loads `snapshotUi` the same way `ui-audit.spec.ts:55-58` loads `auditUi`: `import('/src/utils/uiAudit.ts')` inside `page.evaluate`. So **slice 1 needs no change to the test bridge, `App.tsx`, or `main.tsx`.**
- It switches screens with the rail `data-testid`s and `__rhizomeTest.dispatchAppCommand`, as the audit spec does. No free click or type.
- It is a flashlight. It exits 0 when it finds problems. It is not a push gate. `ui-audit.spec.ts` stays the gate.
- If nothing listens on `BASE_URL`, it prints how to start `pnpm dev` and exits 1. It does not start a server itself (decision 5).

**Done when:** with `pnpm dev` running, an agent answers "does the Chat transcript scroll?" from the command's stdout alone.

## 4. Tests that must fail first

**jsdom cannot do this.** jsdom has no layout engine, so `scrollHeight` and `clientHeight` are always 0, and Tailwind classes have no computed style. The 2026-08-29 plan put the red test in jsdom. In jsdom that test could only pass by stubbing the numbers it claims to measure. So the tests split:

1. **Unit (vitest, jsdom).** The pure classifier `classifyWell({ overflowY, scrollHeight, clientHeight })` returns `canScroll` and a reason. It is red first because the function does not exist. Cases:
   - `overflow-y: visible` with content taller than the box gives `canScroll: false` and reason `not-a-scroller`.
   - `overflow-y: auto` with `scrollHeight === clientHeight` gives `canScroll: false` and reason `no-overflow`. This is the transcript bug.
   - `overflow-y: auto` with `scrollHeight > clientHeight` gives `canScroll: true`.
2. **Real layout (Playwright, regression lane).** `page.setContent` with two fixed fixtures, no app needed:
   - a `flex-1 overflow-y-auto` column under a plain block parent, which must report `canScroll: false`;
   - the same column under a `flex min-h-0` parent of fixed height, which must report `canScroll: true`.
   
   It is red first because `snapshotUi` does not exist. This is the regression the missing scroll box would have failed.
3. **Command (Playwright, regression lane).** Against `pnpm dev`, the Chat screen dump names the transcript well and includes `auditUi` findings. Known baseline duplicates appear in the output, and the command still exits 0.

No PostHog event: this is developer tooling, not a user action. No localization.
