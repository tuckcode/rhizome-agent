# Issue #40 findings — harness vs client

**Origin:** Cursor Grok 4.6 · 2026-09-14 · read-only `gh issue view 40 --comments` + ADR/code audit

**Issue:** [tuckcode/rhizome-agent#40](https://github.com/tuckcode/rhizome-agent/issues/40) — *Decide: is Rhizome a harness, or a client of harnesses?*

## The question (from issue body)

Prime and Hermes are both full MIT agent harnesses, integrated at wildly different depths. ADR-0163 already answered for Prime: **Rhizome does not own the agent loop.** The issue asks whether that identity generalizes, or whether Rhizome should own the loop and treat harnesses as backends — and a third option appeared mid-session: *"pull from several harnesses to create our own"* ([deepseek-harness](https://deepwiki.com/deepseek-ai/deepseek-harness), **unevaluated**).

| Option | Shape |
|---|---|
| **1 — Client** | Rhizome owns no loop; each harness via a standard protocol (ACP worth investigating). Prime depth is the exception, not the template. |
| **2 — Harness** | Rhizome owns the loop; Prime/Hermes become model-and-tool backends underneath. |
| **3 — Borrow** | Rhizome-owned loop, sourcing parts from several harnesses. Makes licensing load-bearing. |

These are not variations — they imply different owners for permissions, edit approval, session state, and what to do when a harness ships a feature Rhizome lacks.

**Settling this unblocks:** whether Hermes integration is a bug or correct-by-design; whether ACP goes on the roadmap; whether adding a fourth agent is a day or a month.

## ADR posture (0163 + 0168)

### ADR-0163 — client for Prime (active, 2026-08-15)

`docs/adr/0163-connect-to-the-prime-daemon.md`

- **Decision:** Rhizome connects to Prime's daemon as one client among several; it does not own Prime's lifetime.
- **Vocabulary:** daemon hosts workers; Rhizome exposes only **session** to the user — same resolution as Hermes Agent (no `hermes agents` command).
- **Consequence:** `prime_session_host.rs` rewritten against the daemon socket; full harness surface (session tree, side questions, RLM depth, cron, etc.) becomes reachable only through daemon, not RPC child.

This ADR answers #40 **for Prime only**.

### ADR-0168 — selective harness doctrine (active, 2026-08-24)

`docs/adr/0168-selective-harness-doctrine.md`, ledger `docs/design/harness-doctrine.md`

- **Decision:** "Rhizome absorbs metabolites, not organs." Prime is the only execution core.
- **Prime verdict:** Rhizome is a **daemon client and policy shell** — renders Prime state, applies foreground ownership / vault / confirmation policy (`harness-doctrine.md` §Source verdicts → Prime Agent).
- **Hermes verdict:** **TAKE contracts, REJECT the stack** — adapt observability, interruptibility, approval, provenance contracts onto Prime; reject Hermes as a second runtime (`harness-doctrine.md` §Hermes Agent).
- **Consequence (leftover acknowledgment):** inherited `ai_models.rs` provider path *"may remain for non-Prime Desktop leftovers, but it is rejected as an architectural path for Prime chat."*

**Does ADR-0168 close #40?** Partially, and only for the filter lens:

- `docs/ASTRA_PACKET.md`: *"#40 | Harness vs client | Filter answered ADR-0168; composition not ratified"*
- `docs/plans/handoffs/2026-08-24-2122-claude-opus-5-shell-dock-and-next-index.md`: *"#40 reads as answered by ADR-0168 … but is still open and needs-info."*

ADR-0168 ratifies **option 1 filtered through Prime** (client + policy shell, no Frankenstein). It does **not** ratify option 3 (composition / borrow-your-own-loop), does not decide ACP, and does not reconcile the measured Hermes integration shape below.

## Measured code asymmetry (issue comment + re-measured 2026-09-14)

From `gh issue view 40 --comments` (2026-08-22) and `wc -l` today:

| | Prime | Hermes |
|---|---|---|
| Rust files | 11 (`prime_*.rs`) | 2 (`hermes_*.rs`) |
| Lines (today) | **~13,442** (`prime_session_host.rs` alone **9,065**) | **301** (`hermes_cli.rs` 214 + `hermes_discovery.rs` 87) |
| Public entry | 26+ fns in session host | 2 fns: `check_cli()`, `run_agent_stream()` |
| Invocation | Daemon socket client, sessions, roster, transcripts | One argv subprocess |

Hermes invocation (`src-tauri/src/hermes_cli.rs`):

```
hermes chat --quiet --source tool -q <prompt>
```

- No session, permissions, edit approval, provenance, or resume on the Rhizome side.
- **`--source tool` is deliberate** (comment at `hermes_cli.rs:50–54`): Hermes treats this as *"third-party integration, hide from the user's session list."* Rhizome suppresses Hermes' own session record; the turn exists only as streamed stdout with a synthetic `hermes-*` session id from `cli_agent_runtime`.

### Two opposite architectures, one repo

| Harness | Code says Rhizome is… | Evidence |
|---|---|---|
| **Prime** | **Client** | ADR-0163 + 9k-line daemon client; Prime owns loop, sessions, transcripts |
| **Hermes** | **Harness (for that turn)** | Rhizome builds prompt, spawns subprocess, owns streamed result, tells Hermes not to remember |

Not two depths on a spectrum — **whichever way #40 resolves, one of these two is currently wrong** (issue comment, 2026-08-22). Doctrine text says reject Hermes stack and be Prime client; Hermes wiring implements the opposite of the Prime path.

Hermes is a **Desktop leftover**: full agent id in the status probe and stream dispatch, but not a product-visible target. Same family as other non-Prime CLI agents (`claude_code`, `codex`, …) sharing `cli_agent_runtime`.

## Pair with #56 — second leftover path

Issue [#56](https://github.com/tuckcode/rhizome-agent/issues/56) documents a different contradiction with the same doctrine. See [`2026-09-14-1602-issue-56-findings.md`](2026-09-14-1602-issue-56-findings.md).

| Leftover | #40 lens | #56 lens | Frankenstein test |
|---|---|---|---|
| **Hermes CLI path** | Rhizome **owns the turn** (harness behavior) | N/A | Removing Prime does not stop Hermes one-shot; Rhizome still spawns and streams |
| **`ai_models.rs` / `api_model`** | Rhizome **owns HTTP + tool loop** (harness behavior) | Second provider path doctrine forbids | Removing Prime does not stop direct provider POSTs |
| **Prime daemon client** | Rhizome **client** (doctrine-aligned) | Prime-only execution for Chat (guarded in `ChatHome.tsx`) | Removing Prime stops core chat |

**Together:** the repo implements **three** integration postures, not two:

1. **Deep client** — Prime daemon (~13k lines).
2. **Shallow harness-over-harness** — Hermes one-shot with session suppression (~301 lines).
3. **Owned provider loop** — `ai_models.rs` + `ai_model_tools.rs` (~1,438 lines) bypassing Prime entirely on some surfaces.

ADR-0168's one-sentence answer (#40 option 1 + filter) matches **(1)** only. **(2)** and **(3)** are inherited Desktop leftovers that contradict both the client identity and each other. #56 is the concrete anchor for **(3)**; #40's issue comment is the anchor for **(2)**.

`docs/design/prime-spoken-surface.md` already warns: do not treat #56's path as a Prime command — it is a Rhizome bypass. The Hermes path is the mirror image: a full harness used as a completion endpoint.
